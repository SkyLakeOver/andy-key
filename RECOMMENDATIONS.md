# Аудит и рекомендации по проекту andy-key (Go + sqlite3 CLI)

Дата аудита: 2026-10-07. Методика: статический анализ кода (main.go, db.go, crypto.go, addresses_islands.go, workstations_islands.go), запуск сервера на порту 9000, тестовое заполнение БД через API согласно схеме (54 проверки: справочники addresses/employees/workstations/hosts/network-equipment/network-mfps/ip-phones, credentials/scripts/tasks, задачи start/stop, журнал, SSR-разделы /api/content/*). Playwright и sqlite3 CLI использовались для проверки входа и структуры данных.

Итог функционального тестирования: **OK=52, BAD=2**. Оба сбоя связаны с критическими проблемами ниже (№1, №2, №3).

---

## Критические проблемы (Critical)

### 1. Обход UNIQUE-ограничения адресов ('' вместо NULL)
**Место:** `db.go` — формирование bindArgs при INSERT/UPDATE в таблице `addresses`.
**Проблема:** пустые поля (`corridor`, `cabinet`, `service_type`) передаются как пустая строка `''`, а не `NULL`. SQLite трактует `NULL != NULL` в уникальных индексах, поэтому UNIQUE-констрейнт обходится и дубликаты создаются с HTTP 200.
**Подтверждение тестом:** негативная проверка «повтор того же адреса» вернула `200 {success:true}` вместо ожидаемого `400` (см. раздел ADDRESSES, метка `[BAD 200!=400]`).
**Рекомендация:**
- При сборке запроса конвертировать пустые строки в `NULL`: `if s == "" { arg = nil }`.
- Либо использовать частичный уникальный индекс с условием `WHERE col IS NOT NULL AND col <> ''`.
- Добавить серверную проверку существования записи до INSERT.

### 2. last_insert_rowid() всегда возвращает 0 между процессами sqlite3
**Место:** `db.go` — получение ID созданной задачи (tasks) и последующая вставка в `task_hosts`, `task_bash_commands`.
**Проблема:** каждая операция запускается отдельным процессом `sqlite3` (spawn на каждый запрос). `last_insert_rowid()` живёт только в рамках одного соединения/процесса, поэтому после INSERT в новом процессе он возвращает `0`. В результате задачи создаются с `task_id=0`, привязки команд и хостов к задаче теряются.
**Подтверждение тестом:** POST /api/tasks вернул некорректный результат (`[BAD 400!=200]` по сценарию), GET /api/tasks → `[]`; task_hosts/task_bash_commands остались без корректного внешнего ключа.
**Рекомендация:**
- Получать ID в том же вызове: `sqlite3 data.db "INSERT ...; SELECT last_insert_rowid();"` (одна строка команды, одно соединение).
- Либо использовать `RETURNING id` (SQLite ≥ 3.35): `INSERT ... RETURNING id;`.
- Долгосрочно — перейти на библиотеку database/sql + mattn/go-sqlite3 (см. №7).

### 3. Пароли credentials сохраняются как числа (hex без кавычек)
**Место:** `db.go` / `crypto.go` — сохранение зашифрованного пароля в таблицу `credentials`.
**Проблема:** hex-строка зашифрованного пароля подставляется в SQL без кавычек. Если hex состоит только из цифр (например `0x...` или чисто числовая последовательность), SQLite приводит значение к numeric-типу. При обратном чтении дешифровка падает — BASH-конструктор задач нерабочий, пароль невозможно восстановить.
**Рекомендация:**
- Всегда оборачивать значения в одинарные кавычки с экранированием (`'` → `''`) или, что правильнее, передавать параметры через механизм bind (`sqlite3 -cmd ".param.bind"` либо параметризованные запросы в Go).
- Хранить шифротекст в base64 — исключает «числовой» affinity.

### 4. Не включены внешние ключи (PRAGMA foreign_keys)
**Место:** `db.go` — инициализация подключения к БД.
**Проблема:** SQLite по умолчанию имеет `foreign_keys = OFF` на уровне соединения. Все FK-связи (employees→addresses, tasks→credentials/scripts, task_hosts→tasks и т. д.) и `ON DELETE CASCADE` не работают. Подтверждено тестом: `DELETE /api/reference/employees/999` (несуществующий ID) вернул `{success:true}`; каскадное удаление адресов оставляет сирот в зависимых таблицах.
**Рекомендация:** выполнять `PRAGMA foreign_keys=ON;` в начале каждого соединения/скрипта; добавить negative-тесты на нарушение FK (ожидаемый 400/500).

## Высокий приоритет (High)

### 5. SQL-инъекции через конкатенацию строк
**Место:** `db.go`, `main.go` — построение всех запросов через fmt.Sprintf/конкатенацию с пользовательскими данными.
**Риск:** классическая инъекция в sqlite3 CLI (поля street/cabinet/name/hostname и др.). Проверено: special-символы (`'`) в payload проходят без экранирования и ломают запрос.
**Рекомендация:** параметризованные запросы (database/sql `?` плейсхолдеры) либо строгое экранирование `'`→`''` во всех точках подстановки.

### 6. SHA-256 с статической солью для паролей пользователей
**Место:** `crypto.go` / `main.go` — хеширование пароля учётных записей панели.
**Риск:** отсутствие per-user соли делает хеши уязвимыми к радужным таблицам; SHA-256 слишком быстрый для паролей.
**Рекомендация:** bcrypt/argon2id (golang.org/x/crypto).

### 7. ensureDefaultAdmin сбрасывает пароль admin при каждом рестарте
**Место:** `main.go` — инициализация приложения.
**Риск:** если админ сменил пароль, после перезапуска сервера он возвращается к дефолтному — тихая деградация безопасности и потенциальный вектор доступа.
**Рекомендация:** создавать админа только при пустой таблице users; никогда не обновлять существующую запись; дефолтный пароль — генерировать случайно и выводить один раз.

### 8. Secure-cookie поверх HTTP ломает вход (в т.ч. Playwright)
**Место:** `main.go` — установка cookie сессии (`Secure: true`).
**Проблема:** при раздаче по HTTP браузер отбрасывает secure-cookie → авторизация не сохраняется, UI/Playwright-тесты входа падают.
**Рекомендация:** `Secure` включать только при TLS (флаг конфига/детект X-Forwarded-Proto); для dev-режима — опция в config.conf.

## Средний приоритет (Medium)

### 9. Нет транзакций и атомарности; spawn sqlite3 на каждый запрос
**Место:** `db.go` — каждая CRUD-операция = отдельный процесс `sqlite3`.
**Риск:** многошаговые операции (task + task_hosts + task_bash_commands) частично применяются при ошибке; высокая задержка; защита от конкурентной записи отсутствует.
**Рекомендация:** переход на `database/sql` + `mattn/go-sqlite3` (или modernc.org/sqlite — без cgo, подходит для Alpine), обёртка составных операций в `BEGIN/COMMIT`, WAL-режим.

### 10. Недостаточная валидация ответов удаления несуществующих ID
**Место:** обработчики DELETE в `main.go`.
**Проблема:** DELETE всегда возвращает `{success:true}`, даже если затронуто 0 строк.
**Рекомендация:** проверять `changes()`/RowsAffected, возвращать 404 при отсутствии записи.

### 11. Файл ключа шифрования `.andy-key.key` (crypto.go, `KEY_PATH`) генерируется и хранится в рабочей директории проекта
**Рекомендация:** вынести в отдельный каталог конфигурации, поддержать путь из config.conf; уже закрыто в .gitignore (`*.key`, `data.db`, `logs/`, бинарник `andy-key`) — не регрессировать.

## Низкий приоритет (Low)

### 12. Логи diagnostic/panel/remote пишутся в ./logs без ротации
**Рекомендация:** добавить ротацию (lumberjack) и ограничение размера; убедиться, что в panel.log не попадают пароли/токены.

### 13. Сообщения валидации разнородны и не стандартизованы относительно кодов HTTP-ошибок
**Рекомендация:** единый формат ошибки `{"error":{"code":..., "message":...}}` для стабильной работы фронтенда и автотестов.

## План исправлений (приоритет)

1. №1–№4 — блокируют корректность данных (один PR: NULL-аргументы, RETURNING id, quoted/base64 secrets, `PRAGMA foreign_keys=ON`).
2. №5–№8 — безопасность и доступность (параметрические запросы через database/sql, bcrypt, фикс ensureDefaultAdmin, флаг Secure).
3. №9–№13 — надёжность и качество (транзакции, changes()-валидация, ротация логов, единый error format).

После исправлений прогнать повторный seed-тест (тестовый скрипт заполнения был удалён вместе с артефактами; критичные кейсы зафиксированы в таблице выше) и Playwright-сценарий входа.
